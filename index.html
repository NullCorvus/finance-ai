Sin Access-Control-Allow-Origin

¿Qué debe verse? La API permite el origen exacto del portal oficial y el del portal de sustentación. El dominio de ejemplo queda fuera de la lista. En el flujo habitual, el navegador llama a /api/ en el mismo dominio del portal y su proxy reenvía la solicitud a finance-api.

Comando de Fish para repetir la prueba

Portal oficial y portal de sustentación 200 con el origen exacto en Access-Control-Allow-Origin. Dominio de ejemplo 400 sin esa cabecera.

for origen in https://finance-staff-web-7caahuohmq-rj.a.run.app https://financiai-portal-demo-1006444199777.southamerica-east1.run.app https://ensayo.example
    echo "Probando origen: $origen"
    curl -si --max-time 10 -X OPTIONS 'https://finance-api-7caahuohmq-rj.a.run.app/api/v1/auth/register' \
        -H "Origin: $origen" \
        -H 'Access-Control-Request-Method: POST' \
        -H 'Access-Control-Request-Headers: content-type' \
        | grep -Ei '^HTTP/|^access-control-allow-origin:'
end
  • for origen in … end repite la prueba una vez por cada dominio. echo imprime el nombre del que se está probando.
  • curl -si --max-time 10 -X OPTIONS URL envía la consulta previa a producción. -s oculta el progreso, -i muestra las cabeceras y --max-time 10 limita la espera a diez segundos.
  • -H "Origin: $origen" simula qué página haría la llamada. Los otros -H indican que el navegador querría enviar un POST con la cabecera Content-Type, como ocurre al enviar JSON.
  • La barra invertida \ continúa el comando en la línea siguiente. | grep -Ei … filtra la salida para mostrar el estado HTTP y, cuando existe, Access-Control-Allow-Origin.

Contraseñas, inicio de sesión y renovación

Contraseñas. Tanto la app como el portal envían el correo y la contraseña por HTTPS. FastAPI verifica la contraseña con Argon2id contra el hash guardado en PostgreSQL. La contraseña se protege en tránsito con HTTPS y en la base de datos se conserva su hash.

Android · Flutter

  1. Inicia sesión

    La app envía el correo y la contraseña a POST /auth/login. FastAPI devuelve dos credenciales.

  2. Usa la sesión

    Flutter envía la credencial de acceso como Bearer en cada petición protegida.

  3. Renueva

    Flutter envía la credencial guardada en el almacenamiento seguro a POST /auth/refresh y recibe un nuevo par.

Portal web · React

  1. Inicia sesión

    El portal envía el correo y la contraseña a POST /staff/auth/login. Administración y Auditoría también verifican un código.

  2. Usa la sesión

    La API entrega dos cookies. El navegador adjunta la de acceso al pedir tickets u otros datos.

  3. Renueva

    El navegador envía la cookie de renovación a POST /staff/auth/refresh y recibe cookies nuevas.

Las rutas del diagrama comparten el prefijo /api/v1.

Una sesión, dos credenciales. La de acceso sirve para las peticiones normales. La de renovación obtiene credenciales nuevas. Son valores aleatorios opacos. La API guarda sus hashes SHA-256 y comprueba la vigencia y revocación de la sesión al recibirlas. Al cerrar sesión se revoca en el servidor.

Vigencia y protección del autenticador

Flutter mantiene la credencial de acceso en memoria. Las cookies del portal llevan HttpOnly, Secure y SameSite=Strict en producción.

E · Estructura y documentación de la API

El contrato de la API es el acuerdo técnico entre el cliente y el servidor. Dice a qué URL llamar, con qué método, qué datos y credenciales enviar y cómo interpretar la respuesta. OpenAPI lo expresa en JSON. Swagger presenta ese mismo documento y permite ejecutar peticiones.

Ejemplo · Consultar cuentas

Flutter llama a GET /api/v1/accounts con una credencial Bearer. Si la petición es válida, recibe 200 y los datos de sus cuentas en JSON. Si falta una credencial válida, recibe 401.

K · Despliegue

Probar FinanciAI

El QR web abre el portal de sustentación. El QR Android abre la descarga del APK.

Estado público de la API

Los servicios corren en Google Cloud Run, en el proyecto finance-ai-api y la región southamerica-east1 (São Paulo). La base de datos de producción es PostgreSQL en Neon.

Cómo se comunican

  1. Android → HTTPS directo a finance-api. Flutter envía la credencial Bearer en la cabecera Authorization.
  2. Navegador → HTTPS al portal. React llama a /api/ en ese mismo dominio. Nginx sirve la interfaz y reenvía esas llamadas por HTTPS a finance-api. El portal oficial y el de sustentación apuntan a la misma API.
  3. FastAPI → PostgreSQL en Neon. La API consulta las cuentas, sesiones y eventos de auditoría. Cloud Run carga la conexión de la base de datos y la clave de cifrado del autenticador desde Secret Manager.

Despliegue automático con GitHub Actions

Push a main → CI exitoso → imagen Docker en Artifact Registry → nueva revisión en Cloud Run → verificación. Las comprobaciones de CI también se ejecutan en develop. El despliegue automático de producción se activa tras el CI exitoso de un push a main.

Backend · despliega FastAPI en finance-api

El workflow deploy.yml recupera el mismo commit que aprobó Backend CI. docker build empaqueta el backend en la imagen backend:<SHA> y docker push la sube a Artifact Registry.

La imagen se usa primero para ejecutar alembic upgrade head y cargar datos de referencia en la base de Neon existente. Después, gcloud run services update cambia la imagen del servicio finance-api. Cloud Run crea una revisión. El workflow consulta /health/ready para verificarla.

Comandos clave del backend 
docker push "$IMAGE"
docker run --rm --env FINANCE_AI_DATABASE_URL "$IMAGE" alembic upgrade head
docker run --rm --env FINANCE_AI_DATABASE_URL "$IMAGE" python -m finance_ai.db.seeds
gcloud run services update "$SERVICE_NAME" --image="$IMAGE"
curl --fail "$URL/health/ready"

Fragmento abreviado. El YAML incluye el proyecto, la región y las referencias de configuración.

Portal oficial · despliega React y Nginx en finance-staff-web

El workflow deploy-staff-web.yml recupera el commit probado por Staff web CI. El Dockerfile utiliza Node para compilar React y copia el resultado a una imagen de Nginx. Esa imagen sirve la interfaz y reenvía las llamadas /api/ al backend configurado.

El workflow comprueba la compatibilidad con FastAPI, sube la imagen a Artifact Registry y obtiene su digest SHA-256, que identifica ese contenido exacto. gcloud run services update instala ese digest en finance-staff-web. Luego se verifica que la revisión esté lista y se prueba el portal desde un navegador.

Comandos clave del portal 
docker build --tag "$image" staff-web
docker push "$IMAGE"
digest=$(gcloud artifacts docker images describe "$IMAGE" --format='value(image_summary.digest)')
deployed_image="${IMAGE%:*}@$digest"
gcloud run services update "$SERVICE" --image "$deployed_image"
node staff-web/deploy/verify-browser.mjs "$url"

Fragmento abreviado. SERVICE es finance-staff-web.
